# Устранение критических уязвимостей PHP2Shell (CVE-2026-109618 / 109619) на EOL-версиях PHP, CentOS 7 и актуальных ветках PHP 8.x

[![CVE](https://img.shields.io/badge/CVE-2026--109618%20%2F%20109619-critical-red)]()
[![CVSS](https://img.shields.io/badge/CVSS%20v4.0-9.2-red)]()
[![PHP](https://img.shields.io/badge/PHP-5.4%20%E2%80%93%208.5-blue)]()

Недавний релиз критических уязвимостей **PHP2Shell** (CVE-2026-109618 и CVE-2026-109619) с оценкой **9.2 по шкале CVSS v4.0** затронул серверы и сайты по всему миру. Это добавило немало головной боли.

## Что произошло

- Уязвимости позволяют злоумышленникам **удаленно выполнять произвольный код** на сервере (RCE) без прохождения аутентификации.
- Проблема затрагивает практически **все версии PHP** (начиная с PHP 5 и вплоть до актуальных веток) во всех стандартных конфигурациях: PHP-FPM, Apache mod_php, php-cgi, FrankenPHP и LiteSpeed.
- Для систем на базе старых, неподдерживаемых версий PHP (ветки 8.1, 8.0, все 7.x и 5.x) **официальных патчей не будет**. Новые версии достаточно просто обновить (инструкция ниже), а самый сложный сценарий — legacy-системы (PHP 5.6–7.4) в статусе End-of-Life (EOL), да еще и на CentOS 7, которая тоже не поддерживается. Но, как говорится, «Нет таких крепостей, которых большевики не могли бы взять».

---

## Коротко: кому что делать

| Система | Действие |
|---|---|
| **PHP 8.2–8.5** на Ubuntu/Debian/Oracle Linux 8–9 | Обновиться через `apt`/`dnf` до патченных версий (8.2.35, 8.3.36, 8.4.27, 8.5.12). После обновления на 8.4+ проверить `memory_limit`: новый жёсткий лимит может ронять тяжёлые скрипты с exit code 137. |
| **PHP 5.6–7.4** на Ubuntu/Debian | Обновиться из репозитория Ondřej Surý (`packages.sury.org`) — там есть бэкпорты безопасности. |
| **PHP 5.4–7.4** на CentOS 7 / Oracle Linux 7 (EOL) | Официальных патчей не будет. Поставить защитное расширение `hp_uploadprogress_guard` (сборка из исходников, инструкция ниже). |
| **Совет «заблокировать multipart в Nginx»** | **Не использовать** — ломает загрузку файлов на проде. |

## Архивные и EOL-системы (CentOS 7, Oracle Linux 7, PHP 5.4–7.4)

Когда ОС и интерпретатор сняты с поддержки, `dnf upgrade` или `yum update` ничего не исправит. Собирать весь PHP из исходников вручную — долго и рискованно. Для таких систем оптимальным решением является использование специализированного защитного расширения **`hp_uploadprogress_guard`** от Hosted Power:

https://github.com/HOSTED-POWER/php_uploadprogress_guard

Модуль на лету перехватывает multipart-запросы, изолирует уязвимые состояния сессий и предотвращает повреждение памяти, полностью заменяя собой официальный патч безопасности.

### Что это за модуль и можно ли ему доверять

`hp_uploadprogress_guard` — открытое расширение от Hosted Power (репозиторий на GitHub, лицензия и история коммитов доступны для аудита). Оно работает на уровне SAPI и не требует патча ядра PHP, поэтому подходит для систем, где обновление интерпретатора невозможно. Ограничения: модуль рассчитан на стандартные SAPI (PHP-FPM, mod_php, php-cgi) и **не заменяет полноценное обновление** — это компенсирующая мера на время, пока вы планируете миграцию с EOL-стека. Перед выкаткой на прод соберите и протестируйте его на стенде с той же версией PHP и тем же SAPI, что и в проде.

### Реанимация YUM на CentOS 7 / Oracle Linux 7

Так как официальные зеркала CentOS 7 отключены, переключаем менеджер пакетов на архивный Vault:

```bash
sudo sed -i s/mirror.centos.org/vault.centos.org/g /etc/yum.repos.d/CentOS-*.repo
sudo sed -i s/^#.*baseurl=http/baseurl=http/g /etc/yum.repos.d/CentOS-*.repo
sudo sed -i s/^mirrorlist=http/#mirrorlist=http/g /etc/yum.repos.d/CentOS-*.repo
sudo yum clean all
```

### Установка зависимостей и компилятора

```bash
sudo yum install -y php-devel gcc make git
```

В логе успешного завершения вы увидите установку пакета `php-devel` и сопутствующего окружения:

```
Installed: php-devel.x86_64 0:7.0.33-42.el7.remi ... Complete!
```

### Сборка модуля

Клонируем исходный код из официального репозитория разработчика. Обратите внимание: утилиту `phpize` и компиляцию нужно запускать строго внутри подпапки `src`, где находится файл `config.m4`:

```bash
git clone https://github.com/hostedpower/php_uploadprogress_guard.git
cd hp_uploadprogress_guard/src
phpize && ./configure && make && sudo make install
```

По окончании успешной сборки система выдаст путь к скомпилированному модулю:

```
Libraries have been installed in:
   /root/php_uploadprogress_guard/src/modules
```

### Установка расширения

Переносим скомпилированный файл `.so` в системную директорию расширений PHP и создаем ini-файл для автоматической подгрузки:

```bash
sudo cp /root/php_uploadprogress_guard/src/modules/hp_uploadprogress_guard.so /usr/lib64/php/modules/
echo "extension=hp_uploadprogress_guard.so" | sudo tee /etc/php.d/99-security-guard.ini
```

### Перезапуск

> ⚠️ **Внимание:** если у вас используется `mod_php` внутри Apache (`httpd`), обычный `reload` или `graceful` не выгрузит старый уязвимый PHP из оперативной памяти процессов. Требуется полный перезапуск службы.

```bash
# для mod_php в Apache
sudo systemctl restart httpd

# для PHP-FPM
sudo systemctl restart php-fpm
```

### Проверка статуса модуля

```bash
php --ri hp_uploadprogress_guard
```

Эталонный лог вывода (все защитные слои должны быть в статусе `active` или `yes`):

```
hp_uploadprogress_guard => enabled version => 3.2.5
multipart/form-data handler replaced => yes
mode => parse session.upload_progress
handler detached => yes session.upload_progress.enabled forced to 0 and locked
(PHP_INI_SYSTEM) => yes out-of-memory exit (_exit(137) while no script is executing) => active unserialize() re-entrancy isolation (destructors during var_destroy) => active
...
```

### Негативный тест: проверяем, что защита реально держится

`php --ri` показывает, что модуль загружен, но не доказывает, что директива действительно заблокирована. Убедимся, что её нельзя переопределить локально.

Создаём тестовый `.user.ini` в корне сайта (или `.htaccess`, если используется `mod_php`):

```ini
session.upload_progress.enabled = 1
```

Затем проверяем фактическое значение из PHP:

```bash
php -r 'echo ini_get("session.upload_progress.enabled"), PHP_EOL;'
```

Ожидаемый результат — `0`. Если вернулась `1`, значит локальный файл переопределил директиву и защита не работает: проверьте, что `hp_uploadprogress_guard` загружается (порядок в `php.d`), и что в конфиге пула не отключена блокировка директив.

После проверки тестовый `.user.ini` удалите — он нужен только для верификации.

### Что мы получили

- ✅ Нейтрализован вектор атаки через глобальные состояния (CVE-2026-109619).
- ✅ Ошибки разбора памяти при отправке multipart-запросов устранены (CVE-2026-109618).
- ✅ Активирована защита от критической Use-After-Free уязвимости в `unserialize()`, обнаруженной параллельно с PHP2Shell.
- ✅ Расширение жестко заблокировало директиву `session.upload_progress.enabled` на системном уровне. Никакие локальные файлы `.htaccess` или `.user.ini` не смогут переопределить ее и открыть уязвимость обратно.

## Поддерживаемые системы Ubuntu и Debian (PHP 5.6 – 7.4)

Для старых веток PHP на системах Ubuntu/Debian лучшим и приоритетным выбором является обновление бинарных файлов из репозитория известного майнтейнера **Ondřej Surý** (`packages.sury.org`), который оперативно бэкпортировал исправления безопасности во все старые релизы.

### Подключение PPA-репозитория и обновление кэша

```bash
sudo apt-get install -y software-properties-common
sudo add-apt-repository -y ppa:ondrej/php
sudo apt-get update
```

### Обновление интерпретатора

Обновляем только интерпретатор и его модули, не затрагивая остальное ПО на сервере (маску версии меняйте под вашу — 5.6, 7.4 и т.д.):

```bash
sudo apt-get install --only-upgrade 'php7.0*' libapache2-mod-php7.0
```

### Перезапуск обработчиков трафика

```bash
# для PHP-FPM
sudo systemctl restart php7.0-fpm

# для Apache (mod_php)
sudo systemctl restart apache2
```

### Проверка пакетов

Выполняем аудит установленных сборок:

```bash
dpkg -l 'php7.0*' | awk '/^ii/{print $2, $3}'
```

В выводе должны появиться новые номера исправленных бэкпортов (например, с индексами безопасности выше `-92` или `-104` в зависимости от ветки).

## Актуальные и поддерживаемые версии (PHP 8.2, 8.3, 8.4, 8.5) на Ubuntu / Debian / Oracle Linux 8–9

Для современных версий PHP выпущены официальные полноценные релизы безопасности: **8.2.35, 8.3.36, 8.4.27, 8.5.12**.

### Процесс обновления на Ubuntu/Debian

Репозиторий Сури здесь также обязателен, так как в стандартной базе Ubuntu (даже 24.04 LTS) свежих веток 8.4 и 8.5 нет:

```bash
sudo apt-get update
sudo apt-get install --only-upgrade 'php8.3*' libapache2-mod-php8.3  # пример для 8.3
```

### Процесс обновления на Oracle Linux 8 / 9 (семейство RHEL)

Если вы используете модули AppStream или репозиторий Remi, обновление выполняется через `dnf`:

```bash
sudo dnf clean metadata
sudo dnf upgrade 'php*'
```

### Обязательный перезапуск служб

```bash
# для PHP-FPM
sudo systemctl restart php8.3-fpm   # или php-fpm на Oracle Linux

# для Apache
sudo systemctl restart apache2      # или httpd на Oracle Linux
```

### Верификация версии

Команда `php -v` должна вернуть защищенный патч-номер:

| Ветка | Минимальная безопасная версия |
|---|---|
| 8.2 | 8.2.35 или выше |
| 8.3 | 8.3.36 или выше |
| 8.4 | 8.4.27 или выше |
| 8.5 | 8.5.12 или выше |

### Важный нюанс для PHP 8.4 и 8.5 (`memory_hard_limit_percent`)

В официальный патч для веток 8.4 и 8.5 разработчики добавили новый механизм защиты — **жесткий лимит памяти**.

**Что это значит:** если ваш тяжелый скрипт (генерация сложных отчетов, импорт больших XML/JSON файлов) упрется в этот лимит, процесс PHP мгновенно завершится операционной системой с кодом ошибки **137**. По умолчанию лимит равен двойному размеру от вашего стандартного параметра `memory_limit` в `php.ini`.

Если после наката патчей на PHP 8.4+ ваши рабочие скрипты начнут падать по OOM (Exit code 137), вам потребуется увеличить лимит выделения памяти (`memory_limit`) в файле `php.ini` для конкретных пулов или скриптов.

## Заключение

Безопасность инфраструктуры — это всегда баланс между защищенностью и доступностью сервисов. Своевременное обновление системных пакетов на актуальных ОС позволяет полностью ликвидировать критические угрозы удаленного выполнения кода (RCE) без остановки бизнес-логики.
